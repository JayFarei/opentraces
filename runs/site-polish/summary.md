## Accuracy flags to resolve before shipping

### privacy-trust — `accuracy_ok = false` (2 BLOCKING mis-attributions)
The section content is accurate to the real v0.6.0 security pipeline and portrays no mock-only feature, but two PROPOSED changes would push wrong tool labels into shipped copy:

1. **EMAIL row mis-attributed.** Proposal labels `jay@company.internal` -> privacy_filter / llm_pii "not regex". WRONG — the regex detector's email_address pattern (secrets.py:269-270) catches it on its own; the allowlist (:36-37) does not cover `@company.internal`. **Label it `regex`.** (privacy_filter is an optional, model-dependent NER detector, often unavailable.)
2. **PATH row self-contradicts.** Demo shows `/Users/jayfarei/` -> `/Users/user/` (literal "user" = EntityMap/normalize_user_paths), but the registry `path_anonymizer` tool HASHES via hash_username() -> `/Users/3f9a1c/`. **Either drop the path row from any tool-named header, keep it generic, or render a hashed token before attributing it to path_anonymizer.**

- Safe as-is: the non-extended header "regex + business_logic applied" is correct for the API-key (regex) and AWS-arn (business_logic) rows; DB URL = regex (NOT business_logic); the business_logic terminal comment "# hostnames, DB URLs, AWS ids" matches describe(); the classifier "verdict only · never echoes the matched value" micro-caption is source-true; "versioned independently (SECURITY_VERSION 0.6.0)" matches version.py.
- Non-blocking nit: the proposed title "Nothing leaves your machine until you name the tool that lets it" is slightly loose (local-first is the bucket; sanitize runs before sync). Keep the README "above the dashed line is local" framing or tighten.
- Once the two attributions are corrected -> flips to **ship**.

### attribution — `accuracy_ok = false` (proposal's central argument is wrong against source)
The proposal's COPY is accurate and overstates no mock-only feature, but its load-bearing accuracy/visual recommendation is false:

1. **FALSE "fabricated cov column" claim.** The proposal calls the green/orange `cov` % a fabricated CI/test signal with "no counterpart in real trail graph output". Source contradicts this — graph_renderer.py:451-479 renders `c:<sha> <subject> <pct>%` with pct = attributed_ratio*100, colored green >=75 / yellow >=50 / red <50, and the commit dot uses the same thresholds. The % is REAL and already IS attribution coverage. **Fix is to LABEL it (dispel the CI-coverage misread), NOT delete it.**
2. **FALSE replacement claim.** "N traces · N files" is the `trail blame commit` SUMMARY line (cli/blame.py:254), NOT what graph commit rows emit. Swapping cov% for it would introduce a NEW inaccuracy. **Do not execute the proposed swap or the top_recommendation built on it.**
3. **OVERSTATED `s:` claim.** `s:` is NOT terminology drift — both `t:` (canonical/ingested traces) and `s:` (attribution-only upstream sessions) are real CLI prefixes. The actionable point survives but narrower: the mock's traces are canonical, so they should render `t:` specifically.

- Genuinely shippable/accurate parts to keep (none depend on the false premise): the two copy rewrites (name "Trails" + de-hedged "Blame renders as a semantic diff"), "renamed symbols" over "renamed files", the overview->drilldown connective affordance between panes, and the proportional 100%-attributed meter.
- Revise: relabel (don't delete) the real %, drop the "N traces · N files"-on-graph swap, fix the s:/t: rows to `t:` for the canonical traces shown (while acknowledging `s:` is real), ship the copy + meter + connective changes.
