# Code Agent Trace Formats and Standards

## Executive Summary

The landscape of code agent trace formats is rapidly consolidating around several complementary standards that serve distinct but overlapping purposes. At the attribution layer, Cursor's **Agent Trace** specification (RFC, January 2026) has emerged as the leading vendor-neutral format for recording which lines of code were generated by AI versus humans, with backing from Cloudflare, Vercel, Google Jules, Cognition, and others [1][2]. At the observability layer, **OpenTelemetry's GenAI Semantic Conventions** and **OpenInference** provide distributed-tracing schemas for monitoring LLM calls, agent reasoning steps, tool invocations, and retrieval operations in production [3][4]. For downstream training, the **Agent Data Protocol (ADP)** and **ATIF (Agent Trajectory Interchange Format)** standardize how multi-step agent trajectories are serialized for supervised fine-tuning and reinforcement learning pipelines [5][6]. Communities publishing trace datasets on Hugging Face, notably Nebius (67K+ OpenHands trajectories), TogetherAI (CoderForge, 51K tasks), and PatronusAI (TRAIL, 148 annotated execution traces), are converging on the Thought-Action-Observation loop as the canonical trajectory primitive [7][8][9]. To maximize downstream value, a community trace dataset should capture: (a) line-level code attribution per Agent Trace, (b) full reasoning chains with tool call schemas per ATIF/ADP, (c) token-level metrics for RL training, (d) OTel-compatible span metadata for observability interop, and (e) content hashes for tracking code movement across refactors.

---

## 1. Introduction

As AI coding agents move from novelty to daily infrastructure, the absence of standardized trace formats creates three compounding problems. First, teams cannot reliably attribute which lines of code were written by which model, making security audits and quality reviews opaque [1]. Second, researchers training next-generation coding agents must wrangle heterogeneous trajectory formats across frameworks like OpenHands, SWE-Agent, and AgentLab, burning engineering effort on format conversion rather than model improvement [5]. Third, observability platforms cannot interoperate on agent telemetry, forcing vendor lock-in for monitoring [3].

This report surveys every major standard, specification, and community convention for capturing code agent traces as of March 2026. It analyzes each format's schema, strengths, gaps, and adoption trajectory, then synthesizes a recommendation for which elements a community trace dataset should incorporate to deliver maximum downstream value to teams training their own solutions.

The research covers six layers of the trace format stack: code attribution (Agent Trace), runtime observability (OpenTelemetry GenAI, OpenInference, Langfuse), trajectory serialization for training (ADP, ATIF), project-level agent instructions (AGENTS.md), existing community datasets (SWE-bench ecosystem, Hugging Face), and the governance landscape (Agentic AI Foundation, NIST).

## 2. The Agent Trace Specification (Cursor)

### 2.1 Overview and Design Philosophy

Agent Trace is an open specification for tracking AI-generated code, published as an RFC (v0.1.0) in January 2026 by Cursor [1][2]. It provides a vendor-neutral JSON format for recording AI contributions alongside human authorship in version-controlled codebases. The specification is released under CC BY 4.0 and is explicitly a data specification, not a product: it defines the schema but leaves storage mechanisms entirely to implementations [1].

The four design goals are interoperability (any compliant tool can read/write), granularity (file and line-level attribution), extensibility (vendor metadata without breaking compatibility), and human readability (no special tooling required) [1]. Critically, Agent Trace declares several non-goals: it does not track legal ownership or copyright, does not track training data provenance, does not assess code quality, and does not require any specific UI [1].

### 2.2 Schema Structure

The fundamental unit is the **Trace Record**, a JSON object with four required top-level fields [1]:

- `version` (string, semver pattern): the specification version, e.g. `"0.1.0"`
- `id` (UUID string): unique trace identifier
- `timestamp` (RFC 3339 date-time): when the trace was recorded
- `files` (array of File objects): the files with attributed code ranges

Optional top-level fields include `vcs` (version control metadata), `tool` (name and version of the generating tool), and `metadata` (open-ended object for vendor/implementation-specific data) [1].

The hierarchical structure flows as: TraceRecord -> File -> Conversation -> Range. Each **File** object requires a `path` (relative from repo root) and a `conversations` array. Each **Conversation** object requires a `ranges` array and optionally includes a `url` (URI linking to the originating conversation), a `contributor` object, and a `related` array for linked resources [1].

The **Contributor** object has one required field, `type`, which is an enum of `human`, `ai`, `mixed`, or `unknown`. The optional `model_id` field follows the `provider/model-name` convention from models.dev, e.g. `"anthropic/claude-opus-4-5-20251101"` [1].

Each **Range** object requires `start_line` and `end_line` (1-indexed integers) and optionally includes a `content_hash` for position-independent tracking (e.g. `"murmur3:9f2e8a1b"`) and a per-range `contributor` override for agent handoff scenarios [1].

### 2.3 Key Design Decisions

**Conversation-grouped ranges.** Ranges are grouped under conversations rather than listed flat, reducing cardinality when one conversation produces many ranges. The contributor is set at the conversation level but can be overridden per range, supporting scenarios where multiple models contribute within a single session [1].

**Line number semantics at recorded revision.** Line numbers reference positions at the recorded VCS revision, not the current file state. The query workflow is: use VCS blame to find the revision last touching line N, look up the trace for that revision/file, find the range containing line N [1]. This design avoids the fragility of tracking moving line numbers across edits.

**Content hashes for code movement.** The optional `content_hash` at range level enables tracking attribution when code moves within or between files during refactoring. The hash format uses `algorithm:value` notation (e.g. `"murmur3:9f2e8a1b"`) [1].

**Vendor extensibility via reverse-domain notation.** Vendors namespace their metadata keys using reverse-domain notation: `dev.cursor` for Cursor-specific data, `com.github.copilot` for Copilot-specific data [1]. This prevents key collisions while keeping the core schema vendor-neutral.

**Storage-agnostic.** The spec intentionally does not dictate where traces are stored. Implementations may use local files, git notes, databases, or any other approach. The reference implementation stores traces as JSONL in `.agent-trace/traces.jsonl` [2].

### 2.4 VCS Support

The `vcs` object supports four version control systems: git (40-character hex SHA), jj/Jujutsu (Change ID, stable across rebase operations), hg/Mercurial (changeset identifier), and svn [1]. The Jujutsu support is notable because jj Change IDs remain stable across amend/rebase operations, which addresses a key limitation of git SHA-based tracking.

### 2.5 Community and Adoption

Contributing organizations include Amp, Amplitude, Cline, Cloudflare, Cognition, git-ai, Jules (Google), OpenCode, Tapes, and Vercel [1][2]. The GitHub repository has 649 stars and 50 forks as of March 2026 [2]. As an RFC, several questions remain unresolved: merge/rebase commit handling and script-generated code attribution are left to implementations [1].

### 2.6 Cognition's Context Graph Perspective

Cognition (the company behind Devin) frames Agent Trace through the lens of "context as the new currency" [10]. Their key insight is that git was designed for bandwidth-constrained environments, storing only line diffs, but the constraint has shifted to context. Every commit systematically discards the reasoning that produced the code [10].

Cognition emphasizes the conversation URL as the core contract: every coding agent maintains a canonical URL for its session/trajectory, and Agent Trace leverages this to link to full context rather than embedding it, keeping traces lightweight while remaining retrievable [10]. They explicitly warn against naively adding prompts as comments, which would bury code. Instead, traces store references to conversations where multimodal, long-form reasoning lives externally, which also keeps PII out of the trace store [10].

For downstream training value, Cognition cites evidence that exposing "hidden reasoning artifacts and prior tool calls" improved SWE-Bench scores by approximately 3 points and cache hit rates by 40-80% [10]. Their thesis: Agent Traced codebases will let agents retrieve "specific context triggered by code," improving accuracy, cost (via cache reuse), and human time lost re-supplying context [10].

### 2.7 MIME Type and Schema Distribution

The MIME type for trace records is `application/vnd.agent-trace.record+json`. JSON Schemas are served at `https://agent-trace.dev/schemas/v1/trace-record.json` using JSON Schema draft 2020-12 [2].

## 3. OpenTelemetry GenAI Semantic Conventions

### 3.1 Overview

OpenTelemetry (OTel) has developed semantic conventions specifically for generative AI systems under the `gen_ai.*` namespace [3]. These conventions, currently in Development status, standardize how LLM calls, agent steps, tool invocations, and related operations are represented as distributed traces, metrics, and events [3]. The work is driven by the OpenTelemetry Generative AI Observability Special Interest Group (SIG), active since April 2024 [3].

### 3.2 Three Signal Types

The conventions capture three primary signals [3]:

**Traces** track each model interaction's lifecycle, covering input parameters (temperature, top_p) and response details (token count, errors). Each interaction is represented as a span with parent-child relationships forming a trace tree.

**Metrics** aggregate high-level indicators: request volume, latency, and token counts, essential for cost management and performance monitoring.

**Events** log detailed moments during model execution, such as user prompts and model responses, providing granular visibility into model interactions.

### 3.3 Key Attributes

The core namespace is `gen_ai.*`, with attributes including `gen_ai.system`, `gen_ai.request.model`, `gen_ai.usage.input_tokens`, `gen_ai.usage.output_tokens`, `gen_ai.provider.name`, and `gen_ai.operation.name` [3]. The `gen_ai.provider.name` attribute acts as a discriminator identifying the telemetry format flavor specific to each provider [3].

### 3.4 Model Spans vs Agent Spans

OTel defines two levels of span conventions [3][11]:

**Model spans** (Semantic Conventions for Generative AI model operations) cover individual LLM API calls with their parameters, inputs, outputs, and token usage.

**Agent spans** (Semantic Conventions for Generative AI agent operations) cover multi-step agent reasoning. A proposal (semantic-conventions issue #2664) introduces conventions specifically for observability of agentic systems, defining attributes for tracing tasks, actions, agents, teams, artifacts, and memory [3][11].

The agentic conventions define three core concepts [3]:
- **Tasks**: minimal trackable units of work describing objectives, decomposable into subtasks
- **Actions**: execution mechanisms (tool calls, LLM queries, API requests, vector DB queries, human input)
- **Memory**: persistent scoped storage of knowledge and context across sessions and agents

### 3.5 Provider-Specific Conventions

Dedicated conventions exist for Anthropic, Azure AI Inference, AWS Bedrock, OpenAI, and Model Context Protocol (MCP) [3]. This allows each provider to extend the base conventions with provider-specific attributes while maintaining interoperability.

### 3.6 Two Parallel Standardization Efforts

Two parallel efforts are developing agent conventions [11]:
1. **Agent Application SemConv** (issue #1732), grounded in Google's AI agent whitepaper, covering application-level agent semantics
2. **Agent Framework SemConv** (issue #1530), targeting frameworks like CrewAI, AutoGen, LangGraph, IBM Bee Stack, Semantic Kernel, and PydanticAI

## 4. OpenInference Specification

### 4.1 Overview

OpenInference is a semantic convention specification for AI application observability built on OpenTelemetry, developed primarily by Arize AI [4]. Every OpenInference trace is a valid OTLP (OpenTelemetry Protocol) trace, ensuring compatibility with any OTel-compatible backend [4].

### 4.2 Span Kinds

OpenInference defines ten span kinds via the `openinference.span.kind` attribute [4]:

| Kind | Purpose |
|------|---------|
| `LLM` | Language model API call with messages, parameters, outputs, token counts |
| `AGENT` | Reasoning step in autonomous agent, may spawn child spans |
| `CHAIN` | Deterministic sequence (prompt formatting, post-processing, orchestration) |
| `TOOL` | Function or external API called by a language model |
| `RETRIEVER` | Query to vector store, search engine, or knowledge base |
| `RERANKER` | Model that reorders candidate documents by relevance |
| `EMBEDDING` | Vector embedding generation |
| `GUARDRAIL` | Input/output moderation check |
| `EVALUATOR` | Automated evaluation (e.g. LLM-as-judge) |
| `PROMPT` | Named prompt template invocation |

### 4.3 Attribute Conventions

Attributes use dot-separated namespaces with zero-based integer indices for list values [4]. For example, `llm.input_messages.0.message.role` addresses the role of the first input message. Key namespaces include `llm.*` (LLM call details), `input.value` (generic input), and `embedding.*` (embedding generation) [4].

### 4.4 Privacy Controls

OpenInference mandates that prompts and completions "must be maskable before export, with per-field granularity," controlled via environment variables [4]. This is critical for community trace datasets where PII must be scrubbed before publication.

### 4.5 Compliance

The specification uses RFC 2119 keywords (MUST, SHOULD, MAY). An implementation is compliant if it satisfies all MUST, MUST NOT, REQUIRED, SHALL, and SHALL NOT requirements [4].

## 5. Langfuse Trace Schema

### 5.1 Data Model

Langfuse, an open-source LLM engineering platform, defines its own trace schema built on OpenTelemetry [12]. A trace represents a single request or operation. Each trace contains one or more observations, which can be nested hierarchically.

### 5.2 Observation Types

Langfuse supports nine observation types [12]:

| Type | Description |
|------|-------------|
| `span` | Durations of units of work |
| `generation` | AI model generations with prompts, token usage, costs |
| `agent` | Application flow decisions using tools with LLM guidance |
| `tool` | Tool calls (e.g. weather API) |
| `chain` | Links between application steps |
| `retriever` | Data retrieval steps (vector store, database) |
| `evaluator` | Assessment of LLM outputs |
| `embedding` | Embedding generation with model, token usage, costs |
| `guardrail` | Protection against malicious content |

The observation type taxonomy closely mirrors OpenInference's span kinds, reflecting convergence in the community on how to categorize agent operations [4][12].

### 5.3 Sessions and Propagation

Traces can be grouped into sessions (e.g. a chat thread). Trace-level attributes like `user_id`, `session_id`, `tags`, and `metadata` propagate to all observations within the trace [12]. Langfuse's observation-centric data model propagates context attributes to every observation, eliminating expensive joins between trace and observation tables at query time [12].

## 6. Agent Data Protocol (ADP)

### 6.1 The Fragmentation Problem

The Agent Data Protocol, published in October 2025 (arXiv:2510.24702), addresses a critical bottleneck in training LLM agents: the fragmentation of trajectory data across heterogeneous formats, tools, and interfaces [5]. Instead of simple input-output pairs, agent training requires trajectories, long sequences of actions and observations representing multi-step interactions. Collecting and curating such data was, before ADP, fragmented across diverse formats with no interlingua.

### 6.2 Schema Design

ADP defines a lightweight schema centered on the **Trajectory** object with three fields [5]:
- `id`: trajectory identifier
- `content`: alternating sequence of actions and observations
- `details`: flexible metadata dictionary for dataset-specific information

**Action Types** (three subtypes) [5]:

1. **APIAction**: structured tool/function calls with `function` (tool name), `kwargs` (arguments dict), and optional `description` (reasoning)
2. **CodeAction**: code execution with `language`, `content` (code to execute), and optional `description`
3. **MessageAction**: natural language communication with `content`

**Observation Types** (two subtypes) [5]:

1. **TextObservation**: text with `source` ("user" or "environment") and `content`
2. **WebObservation**: web interactions with `html`, `axtree` (accessibility tree), `url`, `viewport_size`, and optional `image_observation`

All schemas are implemented as Pydantic models with strict automated validation [5].

### 6.3 The O(D+A) Efficiency Argument

Without ADP, converting D datasets for A agent frameworks requires O(D x A) custom converters. With ADP as an interlingua, only O(D + A) converters are needed: one per dataset to ADP, one per agent framework from ADP [5]. In practice, 13 datasets x 3 agents dropped from 39 custom converters to 16 total. The 13 dataset converters totaled approximately 4,892 lines of code; ADP-to-SFT converters averaged approximately 77 lines each [5].

### 6.4 Training Results

The team converted 13 major datasets into ADP format, creating over 1.3 million training trajectories [5]. Fine-tuning on this unified data delivered an average performance gain of approximately 20% over base models. On SWE-Bench Verified, ADP-trained Qwen-2.5-7B improved from 0.4% to 20.2%, the 14B model achieved 34.4%, and the 32B model reached 40.3%, matching or exceeding Claude 3.5 Sonnet with SWE-Agent [5].

A key finding: models trained on the diverse ADP mix outperformed those fine-tuned on task-specific datasets alone, demonstrating that diversity in training data improves generalization across domains [5].

## 7. ATIF: Agent Trajectory Interchange Format

### 7.1 Overview

ATIF (Agent Trajectory Interchange Format) is a JSON-based specification for logging the complete interaction history of autonomous LLM agents, developed by the Harbor framework [6]. Currently at version 1.6, it is designed to unify the distinct data requirements of conversational logs, explicit action sequences, and replayable data structures, ensuring collected data is immediately usable across debugging, visualization, SFT, and RL pipelines [6].

### 7.2 Root-Level Schema

The root object contains [6]:
- `schema_version` (required): e.g. `"ATIF-v1.6"`
- `session_id` (required): unique run identifier
- `agent` (required): AgentSchema with `name`, `version`, optional `model_name` and `tool_definitions`
- `steps` (required): array of all interaction turns
- `notes` (optional): developer annotations
- `final_metrics` (optional): aggregate metrics
- `continued_trajectory_ref` (optional): link to continuation file
- `extra` (optional): custom root metadata

### 7.3 Step Object

Each step represents a system prompt, user message, or complete agent turn [6]:

- `step_id` (required, integer starting at 1)
- `source` (required): `"system"`, `"user"`, or `"agent"`
- `message` (required): string or ContentParts array (v1.6+)
- `reasoning_content` (optional): explicit internal reasoning
- `reasoning_effort` (optional): e.g. `"low"`, `"medium"`, `"high"`
- `tool_calls` (optional): array of ToolCallSchema objects
- `observation` (optional): ObservationSchema with results array
- `metrics` (optional): MetricsSchema
- `model_name` (optional): per-step model override
- `timestamp` (optional): ISO 8601
- `extra` (optional): custom metadata

### 7.4 Tool Call and Observation Linking

Each ToolCallSchema has `tool_call_id` (unique), `function_name`, and `arguments` (JSON object) [6]. Observations contain a `results` array where each ObservationResultSchema can include a `source_call_id` linking back to the originating tool call, `content` (text or ContentParts), and `subagent_trajectory_ref` for hierarchical agent delegation [6].

### 7.5 Metrics for RL Training

ATIF's MetricsSchema captures fields critical for reinforcement learning pipelines [6]:
- `prompt_tokens`, `completion_tokens`, `cached_tokens`: token accounting
- `cost_usd`: monetary cost per step
- `prompt_token_ids`, `completion_token_ids`: integer token IDs enabling RL without retokenization drift
- `logprobs`: log probabilities per completion token, aligned with `completion_token_ids`

The inclusion of token IDs and logprobs is a distinctive design decision, making ATIF particularly valuable for RL-based training pipelines where these values are required for reward modeling and policy gradient computation [6].

### 7.6 Multimodal Support (v1.6)

ATIF v1.6 added ContentPartSchema supporting `"text"` and `"image"` types, with images referenced by file path rather than base64 to avoid bloat [6]. The convention places images in an `images/` subdirectory relative to the trajectory file.

### 7.7 Multi-Agent Support

ATIF handles multi-agent scenarios through two mechanisms [6]:
- `subagent_trajectory_ref`: array of references to delegated subagent sessions, each with `session_id` and optional `trajectory_path`
- `continued_trajectory_ref`: link to continuation files for trajectories that span multiple files

### 7.8 Version History

| Version | Key Addition |
|---------|-------------|
| v1.0 | Initial release |
| v1.1 | Root-level `extra` field |
| v1.2 | System step observations; clarified `prompt_tokens` includes cached |
| v1.3 | `completion_token_ids` for RL training |
| v1.4 | `prompt_token_ids` |
| v1.5 | `tool_definitions` in AgentSchema |
| v1.6 | Full multimodal support (ContentParts, ImageSource) |

## 8. The Thought-Action-Observation Paradigm

### 8.1 The Canonical Trajectory Primitive

Across all major code agent frameworks, the fundamental trajectory primitive has converged on the **(Thought, Action, Observation)** loop [7][8][13]:

- **Thought** (`ti`): natural language description of the agent's internal reasoning, a diagnostic insight, explanation of program behavior, or proposed fix
- **Action** (`ai`): invocation of an external operation such as editing code, running a test, or calling another tool
- **Observation/Result** (`ri`): response to the action, such as compiler output, test results, execution traces, or error logs

This pattern appears consistently across OpenHands, SWE-Agent, AgentLab, and virtually every SWE-bench-targeting framework [7][8][13].

### 8.2 Framework-Specific Variations

Despite convergence on the TAO loop, frameworks differ in how they serialize it [13]:

- **SWE-Agent (MiniSweAgent)**: uses explicit THOUGHT fields in its format
- **OpenHands**: embeds reasoning within tool calls, using structured JSON logs with message roles (`system`, `user`, `assistant`, `tool`)
- **Gemini CLI**: tracks reasoning in token metrics
- **Claude Code**: conversation-style traces with tool use blocks

OpenHands provides the richest metadata with tool call IDs and security assessments [13]. Its event-stream abstraction captures actions and observations in a perception-action loop analogous to that employed by human developers [13].

### 8.3 MCP Convergence

OpenHands is actively refactoring its action/observation interface to be compatible with MCP (Model Context Protocol) schemas [13]. The goal is that each MCP tool is treated as equivalent to default OpenHands runtime Actions, and all complexity of action schema, tool description, and observation conversions are abstracted into a single "Tool" component [13]. This signals a broader trend toward MCP as the universal tool interface for coding agents.

## 9. AGENTS.md: Project-Level Agent Instructions

### 9.1 Overview

AGENTS.md is a simple, open format for providing project-level instructions to AI coding agents, essentially a README for agents [14]. It uses standard Markdown with no special syntax or extensions. Adopted by over 60,000 open-source projects as of March 2026, it captures build steps, test commands, style rules, validations, and security concerns [14].

### 9.2 Relevance to Trace Formats

While AGENTS.md is not a trace format itself, it provides the project context that should be captured alongside traces. A trace that records an agent editing code without capturing the AGENTS.md instructions that guided that edit loses critical context for reproducibility. Community trace datasets should consider including the AGENTS.md content (or a hash/reference to it) as metadata alongside the traces themselves.

### 9.3 Governance

In December 2025, OpenAI and Anthropic donated AGENTS.md to the Linux Foundation, co-founding the Agentic AI Foundation (AAIF) alongside Anthropic's MCP and Block's Goose [14]. This governance move positions AGENTS.md alongside Agent Trace and MCP as part of a unified ecosystem of open agent standards.

## 10. Community Trace Datasets on Hugging Face

### 10.1 Major Datasets

Several large-scale code agent trajectory datasets have been published on Hugging Face [7][8][9]:

**Nebius/SWE-rebench-openhands-trajectories**: 67,074 trajectories covering 3,792 resolved issues across 1,823 Python repositories, generated using Qwen3-Coder-480B on OpenHands v0.54.0 [7]. This is currently the largest open collection of coding agent trajectories.

**TogetherAI/CoderForge-Preview**: 51,000 distinct open-source tasks with long-horizon, multi-step SFT trajectories [9]. Fine-tuning Qwen-3 32B on this data boosted SWE-Bench Verified from 23.0% to 59.4% pass@1, ranking #1 among open-data models [9].

**PatronusAI/TRAIL**: 148 annotated agent execution traces containing 841 unique errors across reasoning, execution, and planning categories [9]. Collected using OpenTelemetry with the OpenInference standard, making it compatible with real-world tracing software [9].

**SWE-Fuse**: 14,000 validated and correct trajectories combining issue-description-guided and issue-free samples, achieving 60.2% on SWE-bench Verified with 32B parameters [8].

**R2E-Gym**: 3,321 trajectories from 2,048 unique task environments, used to train agents via supervised fine-tuning on thoughts and actions [8].

### 10.2 Format Patterns

These datasets share common structural patterns [7][8]:

- **Message-role format**: `system`, `user`, `assistant`, `tool` roles in conversational structure
- **Tool calls as structured JSON**: with `tool_call_id`, `function_name`, and serialized `arguments`
- **Decontamination**: careful filtering of repositories overlapping with SWE-Bench test sets
- **Iterative data collection**: later iterations use models fine-tuned on previous dataset versions, creating self-improving loops

### 10.3 Scaling Laws for Trajectory Data

Nebius demonstrated a clear positive correlation between training set size and model performance, with resolve rate increasing from 13.5% with zero samples to 39.0% on the full dataset, a 2.9x improvement [8]. This establishes that trajectory quantity matters significantly for downstream performance, making format standardization (which enables dataset combination) a direct contributor to model quality.

## 11. W3C Trace Context and Distributed Tracing Foundations

### 11.1 The Base Layer

W3C Trace Context is the foundational distributed tracing standard, defining the `traceparent` and `tracestate` HTTP headers for propagating trace context across service boundaries [15]. It has achieved W3C Recommendation status and is adopted by all major APM platforms (Datadog, New Relic, Elastic, Dynatrace) and by OpenTelemetry itself [15].

### 11.2 Relevance to Agent Traces

W3C Trace Context provides the base layer upon which both OpenTelemetry GenAI conventions and OpenInference build. Any agent trace format that aims for production observability interoperability should be compatible with W3C trace context propagation. The `traceparent` header carries a trace ID and parent span ID that can link agent traces to broader application traces, enabling end-to-end visibility from user request through agent execution through code deployment [15].

## 12. Governance and Standards Bodies

### 12.1 Agentic AI Foundation (AAIF)

Launched in December 2025 by Anthropic, OpenAI, and Block, hosted by the Linux Foundation [14][16]. AAIF consolidates major open-source contributions: Anthropic's MCP, Block's Goose agent framework, and OpenAI's AGENTS.md [14][16]. Its mission is ensuring AI agents develop on open standards that avoid fragmentation and vendor lock-in.

### 12.2 NIST AI Agent Standards Initiative

NIST's Center for AI Standards and Innovation (CAISI) announced the AI Agent Standards Initiative in February 2026 [16]. The initiative focuses on ensuring autonomous AI agents function securely, serve users reliably, and interoperate smoothly across the digital ecosystem. This signals regulatory attention to agent standards, which may eventually influence trace format requirements for compliance.

### 12.3 OpenTelemetry GenAI SIG

The OTel GenAI Observability SIG drives the semantic conventions for LLM and agent telemetry [3][11]. Two active workstreams, Agent Application SemConv (#1732) and Agent Framework SemConv (#1530), are developing the conventions that will likely become the production standard for agent observability [11].

### 13.2 Complementary, Not Competing

These formats are largely complementary rather than competing [1][3][4][5][6]:

- **Agent Trace** answers "who wrote this line of code and which model was used?"
- **OTel GenAI / OpenInference / Langfuse** answer "how did this agent call perform in production?"
- **ADP / ATIF** answer "how do we serialize this agent's work for training the next model?"

A comprehensive community trace dataset should incorporate elements from all three layers.

## 14. Downstream Value Analysis

### 14.1 Value for Training

For communities training their own coding agents, the most valuable trace elements are [5][6][7][8]:

1. **Complete TAO loops**: Full Thought-Action-Observation sequences with no truncation, enabling supervised fine-tuning on the complete reasoning chain
2. **Token IDs and logprobs**: Critical for RL-based training (RLHF, RLVR, DPO), available in ATIF but not in most other formats
3. **Tool definitions**: The complete set of tools available to the agent during the trace, enabling the model to learn tool selection
4. **Diverse task coverage**: ADP demonstrated that diversity in training data improves generalization, with mixed datasets outperforming task-specific ones
5. **Decontamination metadata**: Clear tracking of which repositories/issues are in the training set to prevent benchmark contamination

### 14.2 Value for Debugging and Reproducibility

For teams debugging agent failures [17][18]:

1. **Model configuration**: Exact model name, version, temperature, top_p, max_tokens, stop_sequences
2. **Full conversation context**: System prompts, prior turns, AGENTS.md instructions
3. **Environment state**: Working directory, file contents at time of action, VCS revision
4. **Error traces**: Exact error messages, stack traces, exit codes from tool executions
5. **Timestamps**: Nanosecond-precision timing for performance analysis

### 14.3 Value for Auditing and Compliance

For security audits and compliance [1][10][17]:

1. **Line-level attribution**: Per Agent Trace, knowing exactly which lines are AI-generated
2. **Model provenance**: Which model (provider/version) generated which code
3. **Conversation linkage**: Ability to pull the full conversation that led to a code change
4. **Content hashing**: Tracking attribution across code movement and refactoring
5. **Immutable audit trail**: Tamper-evident trace storage for regulated industries

### 14.4 Value for Observability

For production monitoring [3][4][12]:

1. **OTel-compatible spans**: Enabling agent traces to flow into existing APM infrastructure
2. **Token usage metrics**: For cost management and optimization
3. **Latency tracking**: Per-step and per-trace timing
4. **Error categorization**: Structured error types (reasoning, execution, planning per TRAIL)

## 15. Recommendations for Community Trace Datasets

### 15.1 Schema Design Principles

Based on this research, a community trace dataset that maximizes downstream value should follow these principles:

**1. Layer the formats.** Use Agent Trace for code attribution metadata, ATIF-compatible step schemas for the trajectory data, and OTel-compatible span metadata for observability interop. These layers are complementary and composable.

**2. Capture complete TAO loops.** Every step should include reasoning (thought), the action taken (with full tool call schema), and the observation (with full output). Truncating any element reduces training value.

**3. Include token-level data when possible.** Token IDs, logprobs, and cached token counts enable RL training pipelines. Without these, the trace is only useful for SFT.

**4. Store tool definitions alongside trajectories.** The complete set of available tools at each step is critical for training models to select the right tool.

**5. Embed model configuration.** Exact model ID (using models.dev convention: `provider/model-name`), version, and all generation parameters.

**6. Reference rather than embed large context.** Follow Cognition's principle: link to conversations and codebases rather than embedding them, keeping traces lightweight while maintaining retrievability.

**7. Support multi-agent delegation.** Use ATIF's `subagent_trajectory_ref` pattern for hierarchical agent traces.

**8. Include decontamination metadata.** Track repository origins and benchmark overlaps to enable clean evaluation splits.

**9. Use content hashing.** Agent Trace's `content_hash` approach enables tracking code attribution across refactors and file moves.

**10. Plan for multimodal.** Include support for screenshots, browser accessibility trees, and other non-text modalities from the start, using file references rather than base64 encoding.

## 16. Open Questions and Gaps

### 16.1 Unresolved in Current Standards

1. **Merge/rebase handling**: Agent Trace leaves this to implementations, but community datasets need a clear convention for how attribution survives rebases [1]
2. **Multi-model attribution within a turn**: When an agent uses a fast model for planning and a strong model for code generation within a single action, attribution granularity is underspecified
3. **Privacy and PII scrubbing**: No standard defines how to redact PII from traces before community publication while preserving training utility
4. **Reward signals**: Neither ADP nor ATIF standardize how to attach reward signals (human feedback, test pass/fail, benchmark scores) to trajectories for RLHF
5. **Incremental trace updates**: How to handle traces that span multiple sessions or are edited after initial recording
6. **Cross-language tool schemas**: Tool definitions vary between Python (Pydantic), TypeScript (Zod), and other ecosystems

### 16.2 Emerging Directions

1. **Context as the new currency**: Cognition's thesis that agent traces will become the primary retrieval mechanism for coding agents, replacing documentation [10]
2. **MCP convergence**: OpenHands' refactoring toward MCP-compatible tool schemas suggests MCP may become the universal tool interface standard [13]
3. **Regulatory requirements**: NIST's AI Agent Standards Initiative may eventually mandate specific trace formats for compliance in regulated industries [16]
4. **Synthetic trajectory generation**: SWE-Synth and similar frameworks demonstrate that synthetic, agent-generated trajectories can outperform real-world data for training [8]

## 17. Synthesis and Conclusions

The code agent trace format landscape in early 2026 is at an inflection point. The key standards are complementary rather than competing, each serving a distinct layer of the stack. Agent Trace handles code attribution, OTel/OpenInference handle runtime observability, ADP/ATIF handle training data serialization, and AGENTS.md handles project-level context.

For a community building trace datasets to train coding agents, the highest-leverage investment is adopting a schema that bridges all three layers. The recommended approach is: use ATIF's step schema for trajectory data (it has the richest support for RL training with token IDs and logprobs), embed Agent Trace attribution metadata for line-level code provenance, include OTel-compatible span metadata for observability interop, and store tool definitions using the emerging MCP-compatible format.

The evidence strongly supports that trajectory diversity matters more than size alone (ADP's cross-domain experiments), that reasoning capture significantly improves downstream agent performance (Cognition's 3-point SWE-Bench improvement), and that standardization itself is a force multiplier (ADP's O(D+A) efficiency argument). A community trace dataset that adheres to these standards will be immediately consumable by the widest range of downstream training pipelines, observability platforms, and audit tools.
