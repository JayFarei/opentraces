## Executive Summary

The academic landscape for agent trace schemas has consolidated around a small number of structural primitives, with the **Thought-Action-Observation (TAO) loop** emerging as the universal trajectory atom across 13+ datasets and 6+ agent frameworks. This survey identifies 20+ papers published between 2022-2026 that propose, evaluate, or depend on specific trace schema choices. The key finding is that opentraces-schema v0.1.0 is well-positioned: its core TAO-based step model, tool call/observation separation, and Pydantic v2 implementation align with the academic consensus, while its additions (security tiers, attribution, hierarchy, outcome signals, token-level cache metrics) address gaps that multiple papers explicitly identify as limitations. Three schema families dominate the space: (1) **training-oriented** schemas (ADP, SWE-smith trajectories, AgentTrek) that optimize for SFT/RL pipeline consumption, (2) **observability-oriented** schemas (OTel GenAI, OpenInference, AgentTrace, AgentSight) that optimize for runtime monitoring and debugging, and (3) **evaluation-oriented** schemas (TRAIL, TRACE, TRAJECT-Bench) that optimize for benchmarking and error diagnosis. opentraces-schema uniquely spans all three as a **collection-oriented** schema, capturing enough structure for each downstream use case while adding the security and provenance layers none of the others provide.

## 1. The TAO Loop as Universal Primitive

### 1.1 Origins: ReAct (Yao et al., 2022)

The foundational schema primitive for modern agent traces traces back to ReAct [1], which established the interleaved Thought-Action-Observation pattern. ReAct demonstrated that LLMs generating both reasoning traces and task-specific actions in alternation outperform methods using either component alone. The trace format is simple: each cycle produces a natural language Thought, a structured Action (tool call or environment interaction), and an Observation (environment feedback). This pattern has become the de facto standard across all subsequent agent frameworks and datasets.

**opentraces-schema alignment**: Our `Step` model with `content` (thought), `tool_calls` (action), and `observations` (observation) directly implements the TAO primitive. The `reasoning_content` field separates chain-of-thought from main content, which ReAct-style systems do not, but which later papers (ADP, AgentPro) found valuable for training data quality.

### 1.2 Formalization in Surveys (2025)

A December 2025 survey on LLM agent methodology [2] formalizes the trajectory schema as **tau = (s_0, a_0, s_1, a_1, ..., s_T)**, generated by iteratively sampling actions and observing state transitions. The LLM processes the current state (comprising observation, memory, and task specification) to produce a reasoning trace and select an action. This mathematical formalization confirms the TAO loop as the canonical structure, not just a ReAct-specific pattern.

### 1.3 Thought-Action-Result Variant (Bouzenia & Pradel, ASE 2025)

Bouzenia and Pradel [3] study 120 trajectories across RepairAgent, AutoCodeRover, and OpenHands (2,822 LLM interactions), normalizing all three into a unified **Thought-Action-Result (TAR)** format. Their schema defines a trajectory as `T = [(t_1, a_1, r_1), ..., (t_n, a_n, r_n)]` where t_i is reasoning, a_i is a tool invocation, and r_i is the environment response. This is structurally identical to TAO with "Result" replacing "Observation," confirming the pattern holds across agents with very different action spaces.

**Validation for opentraces**: The study demonstrates that even agents with radically different internal representations (OpenHands uses structured JSON, SWE-Agent uses bash commands, RepairAgent uses custom APIs) can be normalized to a single step-based format without information loss. This validates our choice to use a unified `Step` model rather than agent-specific schemas.

## 2. Training-Oriented Schemas

### 2.1 Agent Data Protocol (ADP) — ICLR 2026

Already analyzed in depth in [brief 12](12-agent-data-protocol-paper.md). Key schema details: Pydantic v2 models with `Trajectory` containing a flat `content: list[Action | Observation]`. Three action discriminated unions (APIAction, CodeAction, MessageAction) and two observation types (TextObservation, WebObservation) [4]. Validated on 1.3M trajectories across 13 datasets, achieving ~20% improvement on SWE-Bench. The flat list model is explicitly a training optimization, sacrificing hierarchy for simplicity.

**Gaps ADP leaves for opentraces**: No security/anonymization, no attribution, no outcome signals, no hierarchy, no token usage, no system prompt dedup, no content hashing. These gaps are not oversights; they reflect ADP's scope as a training interlingua, not a collection format.

### 2.2 ATIF (Agent Trajectory Interchange Format) — Harbor Framework

ATIF v1.6 [5] provides the most training-pipeline-complete schema in the landscape. Each Step includes an ISO 8601 timestamp, originator (`system | user | agent`), model identifier, dialogue message (with multimodal ContentPart support in v1.6+), and a Metrics model tracking token usage, costs, and logprobs. ATIF also provides `SubagentTrajectoryRef` for multi-agent delegation, directly inspiring our `subagent_trajectory_ref` field.

Key ATIF features not in other schemas:
- **Token IDs and logprobs**: `prompt_token_ids`, `completion_token_ids`, `logprobs` per step, enabling RL without retokenization drift
- **Multimodal content parts**: Array of ContentPart objects for mixed text/image/audio
- **Cost tracking**: Per-step cost alongside token metrics

**opentraces-schema relationship**: ATIF is our primary inspiration for training pipeline interop. We deliberately excluded token IDs/logprobs (not available from agent CLIs) and multimodal parts (code agents are text-primary in v0.1). Our `opentraces export --format atif` path is justified by ATIF's training-pipeline completeness. We added security tiers, attribution, environment metadata, and outcome signals that ATIF lacks.

### 2.3 SWE-smith Trajectories (Yang et al., NeurIPS 2025 D&B Spotlight)

SWE-smith [6] generated 50K task instances from 128 GitHub repositories, producing 26K SWE-agent trajectories. The trajectory format follows SWE-agent's ReAct-style `(thought, action)` pairs per turn, with the agent interacting through an Agent Computer Interface (ACI). The key schema contribution is the task instance format: each instance includes a codebase snapshot, failing test specification, and ground-truth patch, creating a self-contained training unit.

SWE-smith trajectories trained **SWE-agent-LM-32B** to 40.2% on SWE-bench Verified, but ADP's mixed training on the same base model reached higher scores, validating the diversity advantage of unified schemas.

**Validation for opentraces**: SWE-smith's success demonstrates that code agent trajectories specifically (not just general agent data) have direct training utility. Our focus on Claude Code as the first parser targets the same domain.

### 2.4 AgentTrek (Zhu et al., ICLR 2025 Spotlight)

AgentTrek [7] synthesizes web agent trajectories from online tutorials at $0.55 per trajectory. The schema captures two modalities: text-based HTML observations with function-calling API actions, and vision-based screenshot observations with pixel-level actions. Each trajectory includes observations, actions, and chain-of-thought reasoning.

**Relevance to opentraces**: AgentTrek validates that the observation-action-reasoning triple is sufficient for both text and visual agent domains. If opentraces expands beyond code agents, AgentTrek's multimodal schema is a reference point for how to extend observations.

### 2.5 Chain-of-Agents / Agent Foundation Models (Li et al., August 2025)

The Chain-of-Agents paper [8] introduces a trajectory format for distilling multi-agent systems into single-model training data. State-of-the-art multi-agent systems are executed, and their trajectories are recorded as sequences of agent interactions: each step captures the reasoning state, the activated agent, and the agent's output. A progressive quality filtering pipeline removes trajectories with fewer than 5 agent-tool interactions and those with incorrect answers or redundant tool inputs.

Key schema observation: Chain-of-Agents trajectories are "5-20 hops" long, significantly more complex than prior 2-3 hop benchmarks. This validates our `parent_step` and `agent_role` hierarchy for multi-agent sessions that routinely span 50-100+ steps.

### 2.6 Learn-by-Interact (ICLR 2025)

Learn-by-Interact [9] generates trajectories through agent-environment interaction, defining the schema as: given environment E and task I, agent A predicts action a_i based on instruction I and history `H = (o_0; a_1; o_1; a_2; ...; o_{i-1})`. The key innovation is instruction generation from trajectories via sub-trajectory summarization and abstraction, creating aligned instruction-trajectory pairs.

**Validation for opentraces**: The interaction history H is exactly our step sequence. Learn-by-Interact confirms that the trajectory itself can be a source of training signal (not just the final answer), supporting our `output_summary` field on Observations for lightweight trajectory scanning.

### 2.7 Skywork-SWE (June 2025) and SWE-Next (March 2026)

Skywork-SWE [10] generates agent trajectories using OpenHands v0.32.0 with a 100-turn cap per instance. SWE-Next [11] documents a formal dataset schema (Appendix A.10) for scalable SWE task and trajectory collection. Both follow the OpenHands message schema with roles (`system`, `user`, `assistant`, `tool`) and structured tool calls.

**OpenHands message schema** (from Nebius dataset documentation [12]):
```python
role2field_names = {
    "system":    ["role", "content"],
    "assistant": ["role", "content", "tool_calls"],
    "user":      ["role", "content"],
    "tool":      ["role", "content", "name", "tool_call_id"],
}
```

This is essentially the OpenAI chat format, which ADP abstracts away. Our schema is a superset: we use `role: "agent"` instead of `"assistant"` (following ATIF convention), add `reasoning_content`, `token_usage`, `agent_role`, `parent_step`, and other fields.

## 3. Observability-Oriented Schemas

### 3.1 OpenTelemetry GenAI Semantic Conventions (OTel GenAI SIG, 2024-2026)

The OTel GenAI specification [13] defines semantic conventions for agent traces as distributed trace spans. Key schema elements:

- **Agent spans**: `gen_ai.operation.name` = `invoke_agent` or `create_agent`, with span kind CLIENT (remote) or INTERNAL (in-process)
- **Agent attributes**: `gen_ai.agent.name`, `gen_ai.agent.id`, `gen_ai.agent.version`, `gen_ai.conversation.id`
- **Provider discrimination**: `gen_ai.provider.name` with technology-specific conventions for Anthropic, Azure, AWS Bedrock, OpenAI
- **Events**: Opt-in capture of input/output details, evaluation events for quality scoring
- **Metrics**: Request volume, latency, token counts

The specification is **experimental** as of March 2026, with the GenAI SIG actively working toward stability. Provider-specific conventions already exist for Anthropic, which is directly relevant to Claude Code traces.

**opentraces-schema relationship**: OTel is orthogonal, not competing. OTel optimizes for production monitoring (latency, error rates, request patterns), while opentraces optimizes for training data collection (full content, attribution, outcome signals). Our `opentraces export --format otel` is a future interop path. Our `Agent` model (`name`, `version`, `model`) maps directly to OTel's `gen_ai.agent.*` attributes.

### 3.2 OpenInference (Arize, 2024-2026)

OpenInference [14] is a semantic convention specification for AI observability built on OpenTelemetry. It defines span kinds for LLM, Embedding, Tool, Retriever operations. Each span carries the `openinference.span.kind` attribute, with attributes as the primary payload: prompt, response, model name, retrieved documents, tool arguments. OpenInference provides instrumentations for OpenAI, Anthropic, LangChain, MCP, and the Claude Agent SDK.

**Key distinction from opentraces**: OpenInference captures individual operations as independent spans in a distributed trace. opentraces captures entire sessions as self-contained JSONL records. The grain is different: OpenInference is per-operation, opentraces is per-session. Both are needed, for different consumers.

### 3.3 AgentTrace: Structured Logging Framework (AlSayyad et al., AAAI 2026 Workshop)

AgentTrace [15] proposes a schema-based, multi-surface observability model with three trace surfaces:
1. **Operational traces**: actions, state changes, environmental interactions
2. **Cognitive traces**: introspection into agent reasoning processes
3. **Contextual traces**: surrounding situational/environmental information

These are linked under a **unified envelope** realized at runtime via lightweight instrumentation. The paper positions structured traces as enablers of "agent safety, reproducibility, and accountability," closing gaps in existing systems for fine-grained debugging and forensic analysis.

**Validation for opentraces**: AgentTrace's three-surface model maps well to our schema:
- Operational = `tool_calls` + `observations`
- Cognitive = `content` + `reasoning_content`
- Contextual = `environment` + `metadata` + `system_prompts`

The "unified envelope" concept validates our `TraceRecord` as a single self-contained unit bridging all three surfaces.

### 3.4 AgentSight: System-Level Observability via eBPF (Zheng et al., SOSP '25 Workshop)

AgentSight [16] addresses the "semantic gap" between agent intent (LLM prompts) and system effects (syscalls). Using eBPF, it captures:
- **Intent Stream**: decrypted LLM prompts/responses from TLS functions
- **Action Stream**: syscalls, process events from the kernel

A correlation engine joins these into causally-linked traces, then a secondary "observer" LLM performs semantic risk analysis. The approach is framework-agnostic with <3% overhead. In a case study monitoring 6 Claude Code subagents, AgentSight captured 3,153 events, revealing coordination bottlenecks and retry cycles from file locking contention.

**Relevance to opentraces**: AgentSight demonstrates that system-level traces (which our `environment` block partially captures) contain signals invisible at the application layer. The Claude Code subagent case study validates our multi-agent hierarchy model. AgentSight's boundary tracing is complementary: it captures what happens between agent steps, while opentraces captures the steps themselves.

### 3.5 PROV-AGENT: W3C PROV Extension (Souza et al., 2025)

PROV-AGENT [17] extends the W3C PROV standard for agent provenance tracking. Tool invocations are recorded as `prov:Activity` subclasses, arguments as `prov:used`, results as `prov:generated`. LLM interactions follow the same schema with prompts as `prov:used` and responses as `prov:generated`. The agent is a `prov:Agent` linked via `prov:wasAssociatedWith`.

A related paper on LLM agents for workflow provenance [18] implements interactive querying over provenance data using a schema-driven RAG pipeline, demonstrating that structured trace schemas enable natural language querying of agent execution histories.

**Validation for opentraces**: The W3C PROV mapping confirms that agent traces fit cleanly into established provenance models. Our `TraceRecord` could be exported as PROV with minimal mapping: `Step` -> `prov:Activity`, `ToolCall.input` -> `prov:used`, `Observation.content` -> `prov:generated`. This is a potential future export format alongside ATIF and ADP.

## 4. Evaluation-Oriented Schemas

### 4.1 TRAIL: Trace Reasoning and Agentic Issue Localization (PatronusAI, May 2025)

TRAIL [19] provides 148 human-annotated execution traces with 841 unique errors across a formal taxonomy of 20+ error categories (reasoning, planning, system execution). Key schema characteristics:
- Traces captured using **OpenTelemetry + OpenInference** standard
- 1,987 OTel spans total, 575 with at least one error
- Turn-level annotations: span IDs, error category types, evidence, descriptions, impact levels
- Average input tokens >200K, maximum up to 6M tokens per trace

TRAIL's error taxonomy categories include formatting errors (agents failing to structure tool calls correctly), which validates our schema's explicit tool call structure rather than relying on string-formatted commands.

**opentraces-schema validation**: TRAIL demonstrates that OpenInference-captured traces are suitable for detailed error analysis. Our richer schema (with explicit `reasoning_content`, `token_usage`, `outcome` signals) would enable even finer-grained error diagnosis than TRAIL's OTel-based traces.

### 4.2 TRACE: Trajectory-Aware Comprehensive Evaluation (WWW '26)

TRACE [20] introduces a Hierarchical Trajectory Utility Function that quantifies process efficiency and cognitive quality alongside accuracy. The framework addresses the "high-score illusion" where agents achieve correct outcomes through flawed processes. TRACE evaluates the entire trajectory, rewarding systematic planning and evidence grounding.

The key schema contribution is the **Scaffolded Capability Assessment** protocol, which quantifies latent ability by determining the minimum guidance needed for success. This requires trajectory data with step-level granularity, not just final outcomes.

**Validation for opentraces**: TRACE's hierarchical evaluation directly depends on the kind of step-level trajectory data our schema produces. The cognitive quality metrics TRACE computes (evidence grounding, systematic planning) map to our `reasoning_content` and `tool_calls` fields.

### 4.3 TRAJECT-Bench: Trajectory-Aware Benchmark for Tool Use (October 2025)

TRAJECT-Bench [21] evaluates tool-use trajectories with fine-grained metrics: tool selection correctness, argument correctness, dependency/order satisfaction, and breadth (parallel calls) vs depth (interdependent chains). The benchmark synthesizes trajectories that vary along these dimensions.

**Validation for opentraces**: TRAJECT-Bench's distinction between parallel and sequential tool calls validates our step-level model. Our `step_index` ordering plus `tool_calls` list within a step captures both patterns: parallel calls appear as multiple `ToolCall` objects within one step, sequential calls span multiple steps.

### 4.4 Understanding Code Agent Behaviour (Mirchandani et al., ICSE 2026)

This study [22] analyzes trajectories from OpenHands, SWE-agent, and Prometheus, implementing parsers for each to convert into a unified step-based format. Key empirical findings:
- Failed trajectories are consistently **longer** and exhibit **higher variance** than successful ones
- Fault localization shows 72-81% of even failed trajectories correctly identify problematic files
- Success depends more on **approximate** rather than **exact** code modifications

**Validation for opentraces**: The finding that trajectory length correlates with failure validates our `metrics.total_steps` field as a cheap quality signal. The fault localization finding validates our `attribution` block, which tracks which files the agent modified.

## 5. Step-Level Reward and Process Supervision Schemas

### 5.1 AgentPRM: Step-Wise Promise and Progress (November 2025)

AgentPRM [23] constructs Process Reward Models evaluating each decision step based on two dimensions: **promise** (probability of achieving the goal) and **progress** (interdependence between sequential steps). Unlike reasoning tasks where steps have clear correctness, agent action steps require proximity-to-goal and progress metrics.

**Schema implication for opentraces**: AgentPRM's step-level scoring depends on exactly the trajectory structure our schema provides. Future integration could add optional per-step reward scores as a post-processing enrichment, analogous to how we currently compute outcome signals.

### 5.2 STeCa: Step-Level Trajectory Calibration (ACL 2025 Findings)

STeCa [24] identifies suboptimal actions through step-level reward comparison during exploration, then constructs calibrated trajectories using LLM-driven reflection. The framework uses normalized Dynamic Time Warping (nDTW) to calculate trajectory deviation distance.

**Validation for opentraces**: STeCa demonstrates that step-level trajectory data (not just final outcomes) enables sophisticated training improvements. Our per-step `token_usage` and `timestamp` fields provide the granularity STeCa requires.

### 5.3 Agent-R1: End-to-End Multi-Turn RL (November 2025)

Agent-R1 [25] introduces an **Action Mask** to delineate LLM-generated tokens from environmental feedback within trajectories. The framework defines `process_responses_ids` (identifying tool call triggers in token sequences), `extract_tool_calls` (parsing tool invocation requests), and `format_tool_response` (converting raw results for LLM consumption). Environment provides **process rewards** per interaction turn.

**Schema implication for opentraces**: Agent-R1's action mask concept maps to our tool_calls/observations separation. The explicit boundary between "what the agent generated" and "what the environment returned" is exactly what our Step model captures with the `role` field and separate `tool_calls` vs `observations` lists.

### 5.4 Microsoft Agent Lightning / LightningRL (October 2025)

LightningRL [26] converts trajectories to transitions, applies credit assignment, then optimizes with PPO or GRPO. Key architectural detail: the runtime **records traces through OpenTelemetry**, streams them to the training server, and exposes an OpenAI-compatible endpoint for updated models. The **Automatic Intermediate Rewarding (AIR)** module converts system signals (tool return status) into intermediate rewards.

**Validation for opentraces**: LightningRL demonstrates a production architecture where OTel traces feed directly into RL training. Our schema captures richer data than OTel spans (content, reasoning, attribution), meaning opentraces data could feed LightningRL-style pipelines with more training signal per trace. The AIR module's use of tool return status maps to our `Observation.error` field.

## 6. Trajectory Efficiency and Reduction

### 6.1 AgentDiet: Trajectory Reduction (Xiao et al., September 2025)

AgentDiet [27] demonstrates that 39.9-59.7% of input tokens in agent trajectories are waste (useless, redundant, or expired information). Evaluation on Claude 4 Sonnet and Gemini 2.5 Pro across SWE-bench Verified and Multi-SWE-bench Flash shows token reduction with no performance loss (-1.0% to +2.0% relative).

**Schema implication for opentraces**: AgentDiet's waste taxonomy (useless, redundant, expired) suggests that our `output_summary` field on Observations serves a similar purpose: enabling downstream consumers to skip verbose tool outputs without loading full content. The finding that 40-60% of trajectory tokens are waste also validates our schema's emphasis on structural metadata over raw content duplication.

## 9. Competitive Positioning in Academic Context

The academic schema landscape has three layers, and opentraces occupies a unique position bridging all three:

```
Training Layer          Observability Layer        Evaluation Layer
(ADP, ATIF, SWE-smith)  (OTel, OpenInference,     (TRAIL, TRACE,
                         AgentTrace, AgentSight)    TRAJECT-Bench)
    |                         |                         |
    |    opentraces-schema    |                         |
    |    (collection layer)   |                         |
    +------------+------------+-------------------------+
                 |
    Captures enough for all three use cases,
    plus security + attribution + provenance
```

No other schema in the literature attempts to serve all three downstream use cases from a single collection format. ADP optimizes for training, OTel optimizes for monitoring, TRAIL optimizes for evaluation. opentraces captures the superset of data needed for all three, with security tiers ensuring community-safe collection.

## 10. Recommendations for opentraces-schema

### Immediate (v0.1.x)

1. **Cite ADP (ICLR 2026) in schema documentation**: ADP is the strongest empirical validation that unified trajectory schemas improve agent SFT. The paper's 1.3M trajectory scale and ~20% benchmark improvements directly support the opentraces value proposition.

2. **Cite ICSE 2026 code agent study in attribution rationale**: The finding that 72-81% of even failed trajectories correctly identify problematic files validates the attribution block's utility for fault localization.

3. **Add TRAIL error taxonomy as optional metadata enrichment**: TRAIL's 20+ error categories could be applied to opentraces data post-collection, adding evaluation value without schema changes.

### Near-term (v0.2)

4. **Consider per-step reward score field**: AgentPRM [23] and STeCa [24] both demonstrate that step-level rewards significantly improve training. An optional `reward_score: float | None` on Step would enable downstream PRM pipelines.

5. **Add `opentraces export --format otel`**: LightningRL [26] demonstrates OTel trace streaming into RL training. An OTel export would connect opentraces to the observability ecosystem.

### Future

6. **Multimodal observation support**: AgentTrek [7] and ATIF v1.6 [5] both support multimodal content. When opentraces expands beyond code agents, add ContentPart-style observation support.

7. **W3C PROV export**: PROV-AGENT [17] demonstrates the mapping. This would connect opentraces to the scientific provenance ecosystem.
