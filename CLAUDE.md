# opentraces.ai

## Project Overview

Open schema + CLI for capturing agent traces into a private local bucket, applying security scanning and redaction, enriching with attribution/git signals, and optionally publishing as structured JSONL datasets to HuggingFace Hub.

## Stack

- **Language**: Python 3.10+
- **Schema**: `opentraces-schema` (standalone Pydantic v2 package in `packages/`)
- **CLI**: Click-based (`src/opentraces/cli/`)
- **Web review**: removed in v0.4.8 — the Flask web server (`src/opentraces/clients/web/`) and the Textual TUI (`src/opentraces/clients/tui.py`) are deleted; the React SPA under `web/viewer/` is unmaintained; `web` and `tui` verbs were never in the CLI root
- **Marketing site**: Next.js (`web/site/`)
- **Coming soon page**: Static HTML (`web/coming-soon/`)
- **Optional security extras** (opt-in via `opentraces setup <tool>`): `trufflehog` (binary), `transformers` + `torch` (for the `openai/privacy-filter` PII NER), and an OpenAI-compat LLM endpoint (for `llm_pii` and `llm_review`).

## Key Decisions

- Claude Code and Hermes (runtime agents) for v0.2, adapter contract ready for additional parsers
- Own schema (superset of ATIF), export to ATIF via `opentraces export --format atif`
- Sharded JSONL upload (one file per push, never append to existing)
- Attribution derived from Edit tool calls, not unified diff
- Context-aware security scanning (different rules per field type)
- Per-project review policy (auto/review) controlling whether traces need manual approval
- Zero required annotation, all enrichment is deterministic
- Security pipeline is a flat tool registry (`security/tools/_registry.py`). Each tool implements one of three protocols: `Detector` (emits redactable spans — regex, entropy, TruffleHog, privacy-filter, LLM PII, business_logic), `Judge` (verdict without mutation — classifier), or `Transformer` (record rewrite without spans — path anonymizer, capsule_scope). The orchestrator (`security/pipeline.py`) runs tools in canonical order: regex → entropy → trufflehog → privacy_filter → llm_pii → business_logic → path_anonymizer → capsule_scope → classifier. Each tool exposes `enabled(cfg)`, `apply(record, ctx)`, and `describe(cfg)`. Tools are opted in via per-tool `cfg.security.<tool>.enabled` flags (set by `opentraces setup <tool>` commands); there is no top-level privacy-tier knob. The core capture pipeline (`core/pipeline.py::process_trace`) and workflow scripts both call `security.sanitize_record(record, cfg=cfg)` (or pass an explicit `tools=` list) — that's the single public surface for inline sanitization. Records emerge with `metadata.security.tools_applied: list[str]` and `metadata.security.tools.<name>` for per-tool result patches. `SECURITY_VERSION` (currently `0.8.0`) bumps when any tool's detection logic changes or the metadata shape evolves. Session-level LLM review (`opentraces dataset review`) is intentionally NOT in the tool registry — it's an expensive on-demand workflow, not part of the per-record sanitize step. Pipeline health and tool enable state are surfaced by `opentraces doctor` (under `security.tools`) and `opentraces security tools list`. Workflow scripts can also pipe JSON through `opentraces security sanitize --tools <names>` or `--use-config` for language-agnostic sanitization. `0.8.0` (issue #143, seal-family M1) adds ctx/trail-aware companion sanitization: `companion_field_type(path) -> (FieldType, is_path_leaf)` classifies a leaf inside a ctx/trail companion dict, and `sanitize_companion_dict` (a sibling of `sanitize_dict`) walks that dict leaf-by-leaf at its per-leaf field type, stamping a counts+types manifest instead of scanning the companion as one opaque blob. The same bump widens the generic OpenAI key regex to catch hyphenated env prefixes (`sk-live-…`) and adds a tail-consuming path anonymizer (`anonymize_paths(text, consume_tail=True)`) that rewrites a whole `/Users|home/<name>/<tail>` run to one hashed token on embedded substrings, retiring the capsule's weaker `_scrub_identity` into the shared registry tool.
- Post-processors are declared per-project as an ordered list (`post_processors: [{name, command, args, env}]`). They run before dataset publication, after security redaction. Contract: stdin = trace JSON, stdout = trace JSON, exit 0. Non-zero exit / missing binary / invalid output are non-fatal by default, promoted to hard errors under `--strict`. Byte-identical output = no-op. `opentraces doctor` probes configured processors.
- Runtime selection (issue #99, `setup runtime` group). On a multi-install machine (pipx + Homebrew + an editable checkout), the integration glue can each execute opentraces from a different install root; #93 added the DETECTION (`doctor.runtime_provenance`), `setup runtime` adds the TREATMENT. `setup runtime status` presents #93's provenance (never recomputes it); `setup runtime use <pipx|homebrew|source>` re-renders the DISCOVERED integration runners (codex/claude/git/watcher) to the chosen install's interpreter; `setup runtime use-dev [--project]` points them at the editable checkout and writes a project-local `<project>/.opentraces/runtime_selection.json` marker so `doctor.runtime_provenance.dev_runtime_active` reports deliberate dev mode (not drift); `setup runtime remove-duplicates [--keep]` PRINTS (never executes) the data-safe package-removal commands. The chosen interpreter is threaded into every renderer via `capture._interpreter.selected_interpreter` (a contextvar consulted inside `stable_interpreter` with PRECEDENCE over the renderer's local default — so it reaches codex/claude's bare call AND git's explicit-arg call), routed through `stable_interpreter` so the #86 Cellar→opt remap survives selection. OTLP is EXCLUDED from runtime selection in v1 (recorded as a skip row). The watcher re-render is SHIM-ONLY (no launchd/systemd mutation): #65 made the watcher one-shot-per-sweep, so the supervisor re-execs the new shim next interval, and the unit is never removed (`status().installed` unaffected). Engine: `core/runtime_select.py` + `core/integration_repair.repair_installed_integrations(interpreter=, dry_run=, only=)` (`only` re-renders discovered runners even when not fully installed; the legacy `setup upgrade` call keeps its status-gated, byte-unchanged behaviour). Integrations-only, every verb `--dry-run`-able + `--json`-reportable, and DATA-SAFE: never installs/removes a package, never touches `~/.opentraces` bucket/datasets/staging, never a git ref.

- Bucket subsystem (private trace bucket, plan 080 layout v2). Every captured trace lands in a project-local private bucket under `~/.opentraces/bucket/` organized as: per-trace envelope at `bucket/traces/v1/<project>/<trace>/{trace.json, trace_history/, trail.jsonl.gz, context.jsonl.gz, sources.jsonl.gz}` (TraceRecord is the spine; companions are gzip-deterministic JSONL filtered by `trace_id`), content-addressed blobs at `bucket/blobs/v1/<project>/{context,raw}/<hh>/<hash>.{json.gz,blob}` (NOT under `_shared/` by default; per-project namespace), canonical event log mirror at `bucket/events/v1/batches/<seq>-<batch-id>.jsonl.gz` + `bucket/events/v1/index.json` (`schema_version: "opentraces.bucket.events.v2"`), top-level manifest at `bucket/manifest.json` (`schema_version: "opentraces.bucket.manifest.v2"` with `traces[]` array + `events_v1` block). Plan 079's `bucket context-tree {list, show, status, verify}` subgroup is REMOVED — the manifest-only, zero-blob-load inventory read is now `bucket list` (bounded, paginated, accelerator-backed; envelope `opentraces.bucket.list.v1`; `--count` / `--limit` / `--cursor` / facet filters), with the pre-v7 `ctx list` / `ctx info <trace>` / `bucket status` / `bucket manifest` reads kept callable but hidden (superseded by the bare-noun `ctx <trace>` overview and `bucket list`), plus `bucket verify`. The bucket is local-only by default; `opentraces bucket connect` (v7 #162 rename of `setup bucket`, which stays callable hidden) opts into remote-by-default sync against a HuggingFace remote with existing `cfg.hf_token` auth; `--migrate` converts a Plan-079 layout to v2 via write-new-and-swap. Verbs: `bucket repair` (full rebuild from canonical event log + blob store, idempotent; also the v7 target for the old `bucket manifest --heal` / `bucket rebuild`), `bucket verify [--sample N | --full]` (blob content integrity + dangling-ref detection), `bucket reclaim [--apply]` (visible v7 maintenance verb). `bucket prune [--dry-run]` (reachability-based orphan cleanup, never touches events or trace.json) and `bucket prefetch <trace>` (eager pull of one trace's blobs from remote) are now hidden-but-callable; prefer `verify`/`repair`/`reclaim`. - Bucket reads are size-independent (plan 087, the #87 cure). `bucket status` reads the persisted `manifest.json` O(1) (`bucket_status_fast`) and aggregates sync/security counts from a per-row `status` accelerator (`syncable`/`privacy_off`/`security_stale`/`written_at`, maintained on every row-producing path from the authoritative trace-record object envelope), instead of the O(N) full-TraceRecord + security-recompute scan (>400s on a ~1900-trace bucket → 0.20s). The `status` block is DIGEST-EXCLUDED (`_digest_safe_trace_rows` strips it at both digest-material sites; it is absent from the per-row `digest_material`), so `bucket_digest` stays byte-identical to the pre-087 shape — a pre-087 bucket re-digests identically and the cross-machine sync protocol is unchanged. Freshness is honest: `bucket status` stamps a `freshness` block (`stale`/`reasons`/`source`/`rebuild_recommended`) from three O(1) signals — the out-of-band `manifest.dirty.json` marker (dropped by `bucket_security` run + `sync_trace_records_from_local_stores`, cleared by a full `bucket_manifest(write=True)` sweep), a `security_version` skew, and a row-count vs `object_count` gap — and a stale read-model never reports remote-eligible (conservative; push recomputes the authoritative manifest anyway). The race-safe marker is the shared `core/dirty_marker.DirtyMarker` primitive (also backing the trace-search-snapshot marker). `trail track --all` is likewise bounded via `read_events_scoped` (event-type prefilter) instead of two full event-log walks. **HONEST BOUNDARY: `bucket sync push` / `bucket repair` stay O(N) by the sync protocol** — `trace_records.snapshot.digest` + `raw_sources.digest` are full-corpus content hashes the cross-machine digest depends on; size-independent PUSH would require a Merkle/rolling digest = a coordinated cross-machine protocol change, deliberately OUT OF SCOPE. Size-independence is delivered for every READ verb; the only residual O(N) is explicit maintenance/sync verbs.
- Dataset subsystem (local HF-shaped datasets). A dataset is a workflow-driven row projection over one or more traces. `opentraces dataset new <name> --workflow <path>` creates the manifest; `opentraces dataset run` executes the workflow (`--executor current-agent|script`, dry-run, or headless-marker legacy value coerced to `script`); `opentraces dataset review/approve/reject` controls per-row publication state; `opentraces dataset remote create` binds a HuggingFace dataset remote; `opentraces dataset publish` ships approved rows through the shared egress clearance predicate; `opentraces dataset schedule` controls recurring runs; `opentraces dataset status/list/remove` round out the surface. Workflows are skill-format packages (`opentraces workflow create/list/templates/remove`); the bundled template `skill-command-trajectory-eval-v1` lives in `src/opentraces/workflow_templates/` and is materialized into a project on `workflow create <workflow-name> --template skill-command-trajectory-eval-v1`. Seal-family M2 (issues #190-#194) made the seal real: `dataset new --workflow <bogus>` now resolves the workflow BEFORE binding and exits `rc=2` on failure (the dead `sha256:unconfigured` placeholder digest is gone — a bound dataset's digest is always the real resolved one); row lineage is first-class (`DatasetRowIndexEntry.source_trace_id/source_unit_id/source_slice_id` plus a `provenance` dict carrying the full `scope_ref`/`transform@digest`/`bucket_state@digest`/`answers` contract triple per ADR-0008, so a `trace:A-B` span row is traceable back to exactly the slice and workflow build that produced it); `dataset run --sync` projects only bucket data newer than the dataset's recorded watermark cursor (a delta, not a full re-run — a no-op when the bucket hasn't advanced) and advances the watermark on success; `opentraces dataset verify <name>` re-executes the bound workflow against the bucket with its recorded answers in a side-effect-free mode and byte-compares the re-run to the stored rows, classifying the result as `reproduces` / `bucket-advanced` (a superset match — new bucket state legitimately added rows) / `integrity-failure` (a non-zero-exit gate).

- Bursts and patch terminology. A *trace patch* is one Edit/Write tool call — roughly one hunk on one file, NOT one file. A *change burst* clusters file_edit / patch_created nodes by step proximity (default `--burst-gap 35`). `burst.unique_files` is a per-file aggregation (deduped: foreign-agent absolute prefixes and the repo root are stripped so abs/rel variants collapse) keyed by relative path. `burst.patches` is per-hunk (one entry per Edit). The burst's commit lives in `burst_commit_sha` (modal across `patches[*].commit_sha`, falling back to the first git commit observed in the burst's step range via the trace's hook trail) — NOT the trace's `outcome.commit_sha`, which is the LAST commit in the session and is unrelated to the burst. `trace map --bursts` emits a structured `intent` object on the burst node's metadata: `{trigger, most_substantive_spec, spec_chain, burst_commit_sha, commit_subject, commit_body}` (Cluster E). Legacy `intent_text` / `intent_user_step` remain as aliases for `intent.most_substantive_spec.{text, step}` (or trigger when no spec exists). Use `trace map --bursts --no-commit-lookup` (or `trace get --bursts --no-commit-lookup`) to skip the per-burst `git log` lookup on hot/offline paths.
- Workflow→consumer pattern for "trace data at place/time". Workflows produce typed structured row streams from bucket traces; *consumers* read those streams and render to one destination. `core.workflow_runner.execute_workflow(workflow_name, scope, output_path)` is the single execution primitive (the M1 engine collapse, issue #185): it runs a `script` executor that subprocess-runs `<workflow.path>/scripts/build_rows.py` with the one versioned `opentraces.workflow.run_packet.v1` run packet handed over on `OT_RUN_PACKET` + `OT_DATASET_OUTPUT`. `run_dataset_workflow` (the dataset-bound runner behind `opentraces dataset run`) is now lifecycle bookkeeping ONLY *around* that primitive — locks, run dirs, cursors, append, run records — building the same versioned packet as a superset (adding `candidate_query` + dataset provenance/security/privacy_tier fields) and handing execution to `execute_workflow` for the `script` executor; `current-agent` stays a lifecycle-only branch (writes `RUN.md`, executes no script). The permanently-dead `claude-code-headless` executor and its fake-rows test hook are deleted; the executor set is `{current-agent, script}`. The first non-dataset consumer is `core.branch_context.run_branch_workflow` (branch context: base, head, commits, scope_digest), driving the bundled `pr-intent-summary-v1` workflow that emits one row per branch commit with full trace lineage. The PR consumer (`opentraces trail pr render | create | update` in `cli/trail_pr.py`, lifted to a top-level `trail` peer in v7 #165; the pre-#165 `trail blame pr render | create | update` path stays callable but hidden) renders that JSONL as a GitHub PR body (using `entity_join` + `Burst.intent` + `trace_summary` for deterministic synthesis — no LLM) and wraps `gh` for idempotent create-or-update. Future consumers (Slack, dashboards, CI) are new workflows + new renderers under `trail <destination>`, not bespoke modules. Outputs are cached at `<project>/.opentraces/branch_runs/<workflow>/<scope_digest>.jsonl`. A second consumer exists as a prototype (not yet wired into the CLI): the **daily standup** at `examples/standup/` reconstructs the previous day's work, project by project, from bucket traces. Unlike the PR consumer it is narrative/LLM-rendered: `extract_narrative.py` ingests *just enough* per session (the human's asks + the agent's closing wrap-up + files touched, resume/supersede chains collapsed by `session_id`), `STANDUP-PROMPT.md` drives the prose (attempted / landed / still-open), and `render_html.py` renders a readable article in the Capsule editorial style. - Workflow judgment + integrity (issues #186, #187, seal-family M1). Judgment is not an exception to a workflow's determinism, it's a recorded input: a `build_rows.py` script that needs a human/agent call emits structured `JudgmentRequest`s and exits `rc=10` with an `opentraces.workflow.needs_judgment.v1` sidecar; `execute_workflow` raises `WorkflowNeedsJudgmentError`, the CLI surfaces the requests, and `dataset run --answers <file>` re-runs with the recorded answers for a byte-identical result (same handshake shape as `trace slice --judge agent`'s `--answers`). Workflow integrity closes the "digested bytes == installed bytes == executed bytes" gap ADR-0008 names: install-time, `_reject_dotfiles`/`_reject_symlinks` refuse a workflow package or template carrying a non-allowlisted dot-prefixed entry or a symlink; run-time, `execute_workflow` re-verifies the executing package's recomputed digest against the digest the dataset pinned (`verify_workflow_digest`) and, under `dataset run --strict`, fails non-zero before executing on a mismatch (default: warns and proceeds). Trust in a resolved `--workflow` is by provenance (how the package was found), not by directory-vs-file shape.
- The seal-family contract (ADR-0008, `docs/adr/0008-seal-family-contract.md`; PRD #178, milestones M1 #179 / M2 #180 / M3 #181). A projection is *explainable* iff it is a pure function of content-addressed inputs — `scope_ref` (a v7 address) + `transform@digest` (the pinned workflow package) + `bucket_state@digest` (the bucket manifest digest) + `answers` (recorded judgments) — and exactly two things seal that contract: a **dataset** (growing, reviewed rows with full-triple provenance) and a **capsule** (immutable, URL-addressed, redacted mini-bucket of one scope). Egress is governed by ONE shared clearance predicate, `core/egress_clearance.py::clearance_state` (issue #183): a three-way `cleared` / `not_cleared` / `unknown` classification over the same accelerator `status` block `bucket list` already projects, adopted by all three egress doors (`bucket sync push`, `dataset publish`, `capsule share --publish`) instead of each door re-implementing its own lock; `unknown` (status absent) is conservatively withheld, never coerced to safe. `core/isolation.py` (issue #184) is the shared isolated-subprocess primitive behind the workflow script executor and capsule `test`/`replay` runs: it reports `env_scrubbed` (allowlist-only child env — secrets never inherited), `home_isolated` ($HOME redirected), and `network_denied` (probed OS-level egress deny) each honestly, and stamps `sandbox_tier` using the ADR-0008 lattice vocabulary (`none`/S0, `jail`/S1, `container`/S2, `microvm`/S3) — M1/M3 always report `none` (S0), since a same-UID `$HOME` redirect is not real filesystem containment; the tier rises only when real OS-level containment is delivered, never by relabelling.
- Capsule subsystem (`core/capsule/`, `cli/capsule.py`; seal-family M2/M3, issues #195-#199, #156, #157). A capsule is an immutable, URL-addressed seal: a redacted mini-bucket of one usage episode. The visible seal/consume/write surface is `opentraces capsule create <ref>` (REF is a v7 address — a whole `<trace>`, a point `<trace>:<step>`, or a span `<trace>:A-B>` — the address selects scope, no flag soup; `--from-step`/`--to-step` is the explicit span seam), `opentraces capsule get <ref>` (read-only: resolves file/https/`hf://` and prints the envelope, creates no `~/.opentraces` state — a maintainer in a brand-new environment can `get` a capsule with zero setup), and `opentraces capsule import <ref>` (the explicit opt-in write: materializes the carried spine into a schema-valid `TraceRecord` under the reused trace id plus its Trail companion, so an imported capsule projects natively through `map`/`slice`/`trace get`; same capsule id is an idempotent no-op, a different id over the same trace scope-merges). The legacy `capsule export`/`capsule open` spellings stay callable but hidden (a presentation reframe only — the `capsule` command noun and issue wire markers are unchanged, so issue idempotency is preserved). `capsule preview <trace-id>` runs the full redaction pipeline and prints the manifest/business-logic findings/destinations a publish WOULD reach — writes and publishes nothing, the developer-approval checkpoint before anything leaves the machine. `capsule share [--publish]` mints (and optionally uploads) the shareable URL through the same shared egress clearance predicate as `bucket sync push` / `dataset publish`. The capsule's own storage is a scoped, redacted mini-bucket (not a flat blob) so its digest is real. `web/capsule-worker/` is a stateless Cloudflare Worker that renders a published capsule from its URL with zero re-derivation/re-redaction (one outbound fetch of the frozen `capsule.json`, human HTML + progressive JSON endpoints `/summary → /index → /slice /context /trail /repo /environment → /full`); deploy is excluded from this train, the worker ships as a reviewed prototype.
- Capsule replay honesty (seal-family M3, ADR-0008 §4-§5, issues #154, #156, #157). A replay packet leads with four named PROPERTIES — `reproducible`, `gradable`, `scoped`, `sandboxed` — each an `{ok, level, note}` triple derived from a lattice-ranked ordinal (`reproducible` ← `env_tier`, `gradable` ← `oracle_trust`, `scoped` ← `diff_trust`, `sandboxed` ← `sandbox_tier`); `verdict_trust` (`floor`/`low`/`medium`/`high`) is the DERIVED weakest-link `min()` over all four positions, kept as the secondary automation-threshold summary. On today's corpus every honest capsule reports `verdict_trust: floor` and refuses "reproducible" — the resolver that lifts `env_tier` off its `L0` floor is the out-of-train follow-up #202; this is the honesty contract working as designed, not a gap. `opentraces capsule test <ref>` (issue #157) runs the repro in an isolated git worktree or the capsule's hermetic `--from-bundle` archive under `core/isolation.py`'s minimal env allowlist; `--matrix name=v1,v2` sweeps a consumed dependency and reports which version flips the verdict (`resolved_in`); a FOREIGN capsule's captured command is blocked from running on the host by default (`--unsafe-run-on-host` / `--i-own-isolation` override it, both still stamping the honest `sandbox_tier=none` — sandbox v1 adds the block-foreign-by-default GATE and a bundle-hash verify gate, not real OS containment). `capsule share --publish`/`capsule test --from-bundle` scan the exact shipped bundle bytes for secrets before they leave (native TruffleHog over the extracted archive) as a publish GATE, never a trust factor: a finding BLOCKS zero bytes out (`BundleSecretFindingError`) unless `--i-accept-bundle-findings`, and `bundle.secret_scan` is always stamped (clean or blocked, never a secret byte). `opentraces capsule replay --against <ref>` builds the re-pose packet (intent + context + before/after commits + the success-oracle question) for the maintainer's own agent, and `capsule verdict` records the result back onto the issue. Oracle widening (issue #156) additionally captures whether a declared test's execution actually passed at seal time (`captured_pass`), and diff_trust is slice-scoped rather than repo-wide.
- Schema 0.8.0 (issue #200, MINOR bump from 0.7.0, the seal-family train's one schema change). Purely additive `Environment` fields for the future dependency-pin resolver: `resolved_dependencies: list[PinRecord] | None`, `interpreter: Interpreter | None`, `arch`, `platform`, `abi_tag` — all optional, absent by default, and their presence never raises `env_tier` or any trust ordinal on their own (`env_tier` stays at its `L0` floor across the whole M3 stack; the resolver that actually fills them and lifts `env_tier` to `L1` is the out-of-train follow-up #202). The `TraceRecord` wire shape is otherwise unchanged from `0.7.0`.
- Skill-intelligence → verifier → SkillOpt consumer stack. `core/skill_detection.py` (`detect_skill_invocations` / `trace_skill_names`) reads skill usage off each trace — including Codex's read-`.../skills/<name>/SKILL.md` shape — and feeds the trace index. `consumers/skill_intelligence/pipeline.py` projects bucket traces into typed skill episodes / rollouts / eval-tasks (bundled workflow templates `skill-{episodes,eval-tasks,rollouts,update-report}-v1`), surfaced by `opentraces workflow skill-intelligence`. `consumers/verifier_factory/` mines those episodes into a per-skill **rubric** (weighted criteria, each judged against bounded read-only evidence by `deterministic` / `agent` / `human` method) and calibrates it; `cli/skill_verifier.py` (`opentraces skill-verifier status/autoverify/align/score`) is the surface and `consumers/skill_opt/` consumes a calibrated rubric as a reward source via the reward-swap path. The load-bearing invariant is the trust ladder, derived mechanically (never author-set): **agent PROPOSES → factory SCORES against evidence + calibration → human APPROVES** promotion (`manual_required_default_off`). Status is `blocked_<reason>` (reward=null; the reason names the remedy), `provisional_weak_only` (a deterministic non-outcome criterion separates the weak git signal, no human gold, `recommended=False`), or `calibrated` (only fully-trusted status, requires real human gold, always human-gated). Self-aligned/emulated signal can never exceed `provisional_weak_only`. On the current near-one-class bucket (`survival_state` empty, outcomes effectively all-positive) every seed skill correctly returns `blocked_*` — BLOCKED-by-design is the honest answer, not an unfinished feature; the bottleneck is trustworthy labels (deterministic code-fact checks or human ratification — agent "this looks wrong" flags are NOT trustworthy labels), not the framework, which is built and adversarially hardened (10 trust defects closed with sentinels in `tests/test_verifier_trust_fixes.py`). Full design + honest limitations: `kb/projects/opentraces/runs/skill-verifier-factory/{DOCUMENTATION,RUBRIC_DESIGN,CASE_STUDY}.md`; agent procedure: `skill/verifier-creator/SKILL.md`.

## Testing

Use the repo virtualenv for test commands; system Python may not have the
editable packages and CLI dependencies installed.

```bash
source .venv/bin/activate
pytest tests/ -v
```

Focused Trace Trails validation:

```bash
.venv/bin/python -m pytest \
  tests/integration/test_trace_trails_full_stack_demo.py \
  tests/integration/test_trace_trails_installed_runtime_uat.py \
  tests/integration/test_trace_trails_portrayal.py \
  tests/integration/test_trace_trails_corpus.py -q
```

Trace Trails test capabilities:

- `tests/integration/test_trace_trails_full_stack_demo.py` runs the deterministic full-stack mock project: hook-boundary mutation observation, ingest, delayed Git Anchor maturation, Trace Workspace export/open, and user-facing `trail`/`blame`/`graph` projections.
- `tests/integration/test_trace_trails_installed_runtime_uat.py` exercises installed runtime surfaces: `opentraces --json setup git`, a real Git post-commit hook invocation, and `opentraces setup watcher tick --project ... --json` driving session ingest, watcher reconciliation, and anchor maturation.
- `tests/integration/test_trace_trails_portrayal.py` builds the reviewer-facing portrayal packet and checks UAT judgement points for usefulness/usability across watcher, attribution, maturation, and projection surfaces. Human-readable criteria live in `tests/integration/trail_scenarios/reports/trace_trails_portrayal_uat.md`.
- `tests/integration/test_trace_trails_corpus.py` verifies the versioned synthetic corpus at `tests/fixtures/trace_trails_corpus/v1`, including normalized command/API outputs, TrailEvents, Trace Workspace rows, and HF-style dataset artifacts.
- `tests/integration/harness/trace_trails_corpus.py --check` confirms the committed corpus is current; `--update` intentionally regenerates it after accepted scenario changes.

Corpus commands:

```bash
.venv/bin/python tests/integration/harness/trace_trails_corpus.py --check
.venv/bin/python tests/integration/harness/trace_trails_corpus.py --update
```

Opt-in live Claude/tmux UAT is available but must not run in default CI:

```bash
OT_REAL_REPL=1 OT_TRAIL_REAL_REPL=1 \
  .venv/bin/python -m pytest tests/integration/test_trail_real_repl_scenarios.py -q
```

Use the focused Trace Trails suites when validating lineage behavior. Full
`pytest tests/ -v` is still the broad regression command, but unrelated perf
budgets or UI snapshot drift should be triaged separately from Trace Trails
functional evidence.
