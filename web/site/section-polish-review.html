current summary

Two-column hero: left has the eyebrow pill (open traces v0.4.0), the locked h1 "Open data is the new open source.", a two-paragraph subcopy, a 5-method install tab switcher with copy-to-clipboard, a [start capturing] CTA, and a hoverable community-metrics strip. Right is a 7-tab terminal (setup/bucket/trace/trail/ctx/workflow/dataset) where each tab renders a framed CLI panel showing a real command, a rail of labeled rows, a footer note, and suggested next commands.

clarity issues

  • The single clearest value prop never names the core problem. The thesis 'open data is the new open source' lands, but a first-time reader never sees the visceral pain it solves: agent sessions vanish when the terminal closes. The subcopy jumps straight to the mechanism (capture → project → publish) before establishing why anyone should care.
  • The capture → project → publish arc is buried in a 2-sentence paragraph and only legible if you already know the product. Nothing visual reinforces those three steps on the left column; the arc exists only implicitly in the 7 terminal tabs, which read as 7 peers, not one local-first pipeline crossing a publish boundary.
  • The 7 terminal tabs default to tab index 1 (bucket), so the first thing seen is 'private capture store' internals rather than the capture step that starts the story. No signal the tabs are ordered as a pipeline, no progress affordance, no indication of where the local/remote boundary sits.
  • 'traces become the real source' is the crux but is stated as an assertion with no proof above the fold. The reader must infer what a trace contains (prompts, tool calls, reasoning, edits, outcome) from a dense subordinate clause; those concrete contents deserve to be foregrounded.
  • The [start capturing] CTA and the metric strip compete at the same visual weight with no hierarchy between 'install and run it' (primary) and 'browse what the community published' (secondary). A new visitor cannot tell whether the product is a personal CLI or a community dataset hub.

accuracy issues

  • Subcopy says workflows 'project compliant dataset rows.' 'Compliant' overstates the guarantee — every security tool is default-OFF and opt-in per workflow, and the docs warn risk is "reduced, not removed." Use 'reviewed' / 'security-scanned' / 'schema-valid' which the product actually delivers.
  • The setup tab row 'git + watcher post-commit · blame on' slightly overstates the watcher (polling-based today; real-time inotify deferred) and conflates the watcher with blame, which is a separate opt-in 'setup git' correlator step.
  • The ctx tab footer 'Reconstruct the model's view at any step' is defensible (shipped framing) but is the closest-to-the-line claim — CLAUDE.md's honest-scope says the JSONL path returns a session-level approximation; true per-step only via the OTLP receiver. Keep, do not strengthen.
  • No mock-only Hub features leak into the hero (good). Intents-as-catalog, Evals/SOPs, Alerts/Slack, Self-Improving PRs, and Standup are correctly absent; the terminal panels correctly hedge ('remote ... manual', 'security regex · entropy opt-in'). Preserve this discipline.
  • Agents Pi/Codex/Claude shown as 'ready' in setup is accurate (Claude Code + Codex via hooks, Pi via npm); install paths are real shipped paths. No change needed; verified.
